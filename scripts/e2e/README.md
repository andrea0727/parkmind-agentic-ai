# E2E on real ports

Runs the initial planning graph against **real** dependencies and records what happened per scenario (33 scenarios).

## Requires real credentials (this is not a CI test)

| What | How |
|---|---|
| Anthropic LLM | `ANTHROPIC_API_KEY` in `.env` (model: `ELICIT_MODEL`, default Claude Haiku 4.5) |
| Postgres | `DATABASE_URL` in `.env`, migrated (`alembic upgrade head`); `docker compose up -d` gives you one |
| Throwaway Postgres DB with an empty catalog | `createdb parkmind_edge`, migrate it, and set `E2E_EDGE_DATABASE_URL` (default `postgresql://parkmind:parkmind@localhost:5432/parkmind_edge`). Used by `proveedor_caido_db_vacia` and `happy_catalogo_vacio`; the latter fills its catalog, so recreate the DB to re-run them |
| ThemeParks, Open-Meteo | Public internet access; no key |

Each full run makes real LLM calls (about 35, roughly 15 minutes). Results depend on the real clock: several scenarios use the park time at run time.

## Run

```bash
python scripts/e2e/capture.py                      # all 33, skipping ones already in docs/e2e/raw/
python scripts/e2e/capture.py espanol grupo_de_1   # only these
FORCE=1 python scripts/e2e/capture.py              # re-capture everything
python scripts/e2e/build_report.py                 # no credentials needed: docs/e2e/raw -> docs/e2e/REPORT.md (raw/ is git-ignored; run capture.py first)
```

Optional env vars: `E2E_NOW` (HH:MM park time the whole run pretends it is; default `10:00`, so results never depend on the real time of day), `E2E_RAW_DIR`, `E2E_BAD_DATABASE_URL` (a port nobody listens on, to simulate a DB outage).

## Interactive Allure report (not committed)

Every `build_report.py` run is **kept**, not overwritten. It needs the Allure CLI (`brew install allure`) and writes:

```
build/e2e/runs/<capture time>_<passed>of<total>/
    allure-results/   allure-report/   raw/   REPORT.md
build/e2e/latest  -> newest run
```

The previous run's Allure `history/` is carried into the new report, so the Trend graph and each scenario's History tab show how results change run over run (a scenario keeps its history as long as its id in `scenarios.py` stays the same). Rebuilding the same captures reuses that run's folder instead of creating a duplicate. Each scenario has a plain-language title, an explanation of what it tests, the steps, the expected result and the exact guest message(s) (`DOCS` in `build_report.py`).

```bash
python scripts/e2e/build_report.py                         # adds a run and regenerates the report
(cd build/e2e/latest/allure-report && python -m http.server 8766)   # Allure needs HTTP; index.html does not work via file://
```

Delete `build/e2e/runs/<folder>` to forget a run.

## Files

- `harness.py`: env loading, Anthropic extractor, stage spies.
- `scenarios.py`: the 33 scenarios and the outage injectors (`provider_down`, `db`).
- `capture.py`: runs scenarios, writes `docs/e2e/raw/<id>.json` (DB passwords are scrubbed).
- `build_report.py`: judges each capture against its expected behavior and renders `REPORT.md` and the Allure results.
- Docs: `docs/e2e/SCENARIOS.md` (scenario tables), `docs/e2e/REPORT.md` (generated by `build_report.py`, git-ignored).
